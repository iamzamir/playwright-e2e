## 1. Problem
`configs/setup.js` builds every URL and setting by assigning `process.env` keys, separately for each of the four environments (QA, INTEROP, PSR, STAGE, the RnD stage environment), and for each `URL_MODE` and `GATEWAY_TYPE`. The same endpoints are written up to four times, differing only by gateway segment. A new endpoint means four edits and an easy miss (the branches already have different key counts). It also always sets `DEBUG = true` and `PERFORMANCE_RUN_ITERATIONS = 3`, overriding callers.

## 2. Evidence (verified 2026-10-19 on `main` @ `f265f9fb3`)
- `configs/setup.js`: 513 lines, 340 `process.env.X =` assignments (`grep -c "process.env\.[A-Z_]* *=" configs/setup.js`).
- Line 9: `process.env.DEBUG = true;` (unconditional). Line 11: `process.env.PERFORMANCE_RUN_ITERATIONS = 3;` (unconditional).
- Four environment branches with different key counts: QA 79, INTEROP 84, PSR 61, STAGE 61. Not every endpoint exists in every environment.
- The gateway segment is **not** the `ENVIRONMENT` name, and ALM uses a separate segment:

  | `ENVIRONMENT` | `PSENV` | Gateway segment | ALM segment | Gateway | `URL_MODE=NEW` | Default `REALM_KEY` (Gravitee) | Gravitee domain |
  |---|---|---|---|---|---|---|---|
  | QA | QA | `cbp/qa` (+ `qa/` prefix in places) | `staging` | Azure or Gravitee | Supported (legacy) | `cbpf-test27` (forced) | `interop.na.blueyonder.dev` |
  | INTEROP | INTEROP | `cbp/interop` | `staging` | Azure or Gravitee | Supported (legacy) | `REALM_KEY` or `cbpf-test23` | `interop.na.blueyonder.dev` |
  | PSR | PSR | `cbp/psr` | `psr` | Azure or Gravitee | **Not supported** | `popspsr-psr` (forced) | `psr.na.blueyonder.dev` |
  | STAGE | STAGE | `cbp/demo` | `demo` | **Gravitee only** (forced) | **Not supported** | `cbprndsg-demo` (forced) | `interop.na.blueyonder.dev` (`STAGE_GRAVITEE_DOMAIN_SUFFIX`) |

- `URL_MODE=NEW` (short `po/api/v1`, `ai/api/v1`, `lm/api/v1` paths) applies only to QA and INTEROP, and is discontinued: keep it working there, but don't extend it. Today the PSR and STAGE branches also carry `useOldUrls ? ... : "po/api/v1/..."` ternaries, but those NEW paths were never valid there and nothing runs them: the backend workflow's `url-mode` input is offered only with `environment` INTEROP or QA (`playwright-po-backend-suite.yaml`), and no `package.json` script sets `URL_MODE` for PSR or STAGE.
- Paths that break the pattern and need per-environment overrides, not a placeholder: QA foundation paths (`cbp/foundation-bff`, `cbp/foundation-simulation`, `cbp/foundation-model`, `cbp/foundation-interactive-planning`); INTEROP's foundation paths; PSR `PLANNING_INSTANCE` = `cbp/cbp/psr/foundation/interactive-planning/planningInstance`; `UI_FIELDS_BASE` uses the OLD path in both URL modes.
- Environment-specific behaviour beyond URLs:
  - STAGE forces `GATEWAY_TYPE=GRAVITEE`, `REALM_KEY`, `REALM_NAME` and `REALMS` (so INTEROP values in `.env`/CI can't leak in), honours incoming `POLINK`/`PSLINK`/`SNALINK` (default empty), and reads only `STAGE_GRAVITEE_*` overrides, never the generic `GRAVITEE_*` ones.
  - INTEROP Gravitee reads `configs/gravitee-realms.json` by `REALM_KEY`, supports `REALM_KEY_SOURCE`/`REALM_KEY_TARGET`, and a per-realm client `GRAVITEE_CLIENT_ID_<REALM_KEY>`.
  - Secret variable names are inconsistent across environments: `CLIENT_SECRET_QA` / `CLIENT_SECRET_IOP`, `QA_GRAVITEE_*` / `PSR_GRAVITEE_*` / `STAGE_GRAVITEE_*` / `GRAVITEE_*`, and `SQL_SERVER_<QA|IOP|PSR|STAGE>` (INTEROP is `IOP`).
  - Unset `ENVIRONMENT` defaults to INTEROP; an unknown value matches no branch and silently leaves the URLs unset.
- Line 505 builds `NAVIGATE_TO_IDENTITI_AND_ACCESS` from `IDENTITY_AND_ACCESS` before line 506 sets it, so it ends in `undefined` unless `.env` sets it.
- `util/gateway.util.ts` `applyRealmKeyOverride()` rewrites `LUMINATE_PORTAL_URL`, `API_BASE_URL`, `AUTH_URL`, `REALM_*`, `CLIENT_*` and every `NAVIGATE_TO_*` key in `process.env` **at test time** when test data pins a `REALM_KEY`. A config frozen at startup would go stale there.
- `setup.js` is required by `playwright.config.ts`, `playwright.sauce.config.ts`, `playwright.visual.config.ts`, `global-setup.ts` and `scripts/codegen.ts`. `ENVIRONMENT`/`PSENV` are also read by `fixtures.ts`, `portal.page.ts`, `scripts/run-po-backend-batches-parallel.js`, `scripts/triage/verdict.js` and specs, and ~27 specs `require('testdata/' + PSENV + ...)`.
- Specs read `process.env` directly: 221 spec files; 128 distinct keys across `tests/`, `pageobjects/` and `util/`.
- Gateway prefixes are described in learnings ("Environment and setup"). `setup.js` prints `[setup] ...` lines that people and triage read; keep them.

## 3. Scope
- **In:**
  - Keeping `URL_MODE=NEW` for QA and INTEROP only (legacy, discontinued: kept, not extended).
  - `configs/env/environments.ts`: one row per environment (QA, INTEROP, PSR, STAGE) holding `psenv`, `gatewaySegment`, `almSegment`, allowed gateways, forced values, UI links, realm names and IDs, Gravitee defaults, and secret variable *names*.
  - `configs/env/endpoints.ts`: one row per endpoint, with per-environment availability and overrides.
  - `configs/env/index.ts`: builds a typed `Config` and, for compatibility, writes the same `process.env` keys.
  - A parity script.
  - Switching `setup.js` to call the builder.
  - Migrating `util/api.util.ts` and other utils to read `Config`.
- **Out:**
  - Changing any URL value. This is a pure refactor, apart from the fixes listed in step 4.
  - Migrating specs and page objects off `process.env` (221 files). Do that in a follow-up task once utils are done.
  - Renaming secret variables in `.env`, CI secrets or workflows.

## 4. Implementation steps
1. **Snapshot the current output.** Write `scripts/env-parity.js`. Derive the combinations by reading `setup.js`'s `if` branches, not from this list:
   - `ENVIRONMENT`: unset (defaults to INTEROP), QA, INTEROP, PSR, STAGE.
   - `URL_MODE`: OLD, NEW (anything other than `OLD` is NEW). NEW is a real combination for QA and INTEROP only; for PSR and STAGE, run NEW once each to record the fallback in step 4.
   - `GATEWAY_TYPE`: AZURE, GRAVITEE. Keep STAGE × AZURE: it must produce the same output as STAGE × GRAVITEE, which proves the forcing.
   - INTEROP × GRAVITEE extras: each `REALM_KEY` in `gravitee-realms.json`, plus `REALM_KEY_SOURCE`/`REALM_KEY_TARGET` set.
   - Per environment, a run with the incoming overrides set (`REALM_KEY`, `PSLINK`, `USER_TOKEN_REALM`, `STAGE_GRAVITEE_*` / `GRAVITEE_DOMAIN_SUFFIX`, `SQL_SERVER_<suffix>`) and a run without them.

   For each combination, run `setup.js` in a child process with a clean env (secrets replaced by placeholders like `__SECRET_<NAME>__`) and dump the resulting `process.env` keys and values, plus the `[setup]` stdout lines, to `reports/env-parity/<combo>.json`. Run it with `dotenv` disabled (or `DOTENV_CONFIG_PATH` pointing at an empty file) so `.env` doesn't leak in. The missing-credential `throw` paths (Gravitee without client ID or secret) are combinations too: record the error message. Commit nothing from `reports/`.
2. **Tables.**
   ```ts
   export type EnvName = 'QA' | 'INTEROP' | 'PSR' | 'STAGE';
   export interface EnvironmentDef {
     psenv: EnvName; gatewaySegment: string; almSegment: string; sqlSuffix: 'QA' | 'IOP' | 'PSR' | 'STAGE';
     gateways: ReadonlyArray<'AZURE' | 'GRAVITEE'>;            // STAGE: ['GRAVITEE']
     supportsNewUrls: boolean;                                 // true for QA and INTEROP only; NEW mode is discontinued
     forced: Partial<Record<string, string>>;                  // e.g. STAGE REALM_KEY/REALM_NAME/REALMS
     links: { po: string; ps: string; sna: string; honourIncoming: boolean };
     gravitee: { defaultRealmKey: string; realmKeyForced: boolean; domainSuffix: string; overridePrefix: string; clientIdVar: string; clientSecretVar: string };
     /* realm names/IDs, Azure hosts, secret variable names */
   }
   export interface EndpointDef {
     key: string; service: 'po' | 'ai' | 'lm' | 'uif' | 'ps' | 'alm' | 'iam' | 'foundation' | 'other';
     oldPath: string; newPath?: string;                        // placeholders: {gw}, {alm}; newPath absent = same in both modes; used only where supportsNewUrls
     envs?: EnvName[];                                         // absent = all environments
     overrides?: Partial<Record<EnvName, { oldPath?: string; newPath?: string }>>;  // e.g. PSR PLANNING_INSTANCE, QA foundation paths
   }
   ```
   Secrets stay in env vars; the tables hold only variable *names* for them. `newPath` is legacy: a new endpoint gets `oldPath` only, and the builder reads `newPath` only for environments with `supportsNewUrls` (QA, INTEROP). Drop the PSR and STAGE NEW-path ternaries rather than porting them. The `Record<EnvName, ...>` type makes the compiler reject an environment row that's missing.
3. **Builder.** `configs/env/index.ts` exports:
   - `buildConfig(env: NodeJS.ProcessEnv): Readonly<Config>` (pure; throws on an unknown `ENVIRONMENT`, see step 4).
   - `applyToProcessEnv(config)`, which writes the legacy keys.
   - `getConfig()`, which returns the active config.

   `setup.js` becomes a thin wrapper that calls `applyToProcessEnv(buildConfig(process.env))` and keeps its `[setup]` log lines. If loading TypeScript from `setup.js` is a problem (`setup.js` is required by three Playwright configs, `global-setup.ts` and `codegen.ts`), compile `configs/env` to JS with a small `tsc -p` step, or write the builder in JS with JSDoc types.

   **Runtime realm override:** `applyRealmKeyOverride()` still changes hosts per test. Either have it call `buildConfig({ ...process.env, REALM_KEY })` and swap the active config, or make `getConfig()` derive host-dependent values (`LUMINATE_PORTAL_URL`, `API_BASE_URL`, `AUTH_URL`, `NAVIGATE_TO_*`) from the current `process.env` on each call. Don't hand out a config frozen at startup for those keys. Move the `NAVIGATE_TO_*` composition into one helper used by both the builder and `gateway.util.ts`.
4. **Parity.** Run `scripts/env-parity.js` against the new `setup.js` and diff with step 1. Every combination must be identical, except these deliberate fixes, which the PR lists:
   - `DEBUG`: honour an incoming value; default `true` (nothing in the repo reads it, so the old always-`true` default stays).
   - `PERFORMANCE_RUN_ITERATIONS`: honour an incoming value; default 3.
   - Unknown `ENVIRONMENT` (not QA, INTEROP, PSR or STAGE): throw with the list of valid values, instead of silently leaving URLs unset. Unset still defaults to INTEROP.
   - `URL_MODE=NEW` on PSR or STAGE: resolve the OLD paths and print `[setup] URL_MODE=NEW is only supported for QA and INTEROP; using OLD for <ENV>`, with the effective `URL_MODE=OLD` on the main `[setup]` line. Today these produce `po/api/v1/...` paths that don't exist there; nothing runs them (see section 2), so this changes no scheduled run. QA and INTEROP NEW output must stay identical.
   - `NAVIGATE_TO_IDENTITI_AND_ACCESS`: build it after `IDENTITY_AND_ACCESS` is set (today it ends in `undefined`). Confirm nothing relies on the broken value first.
5. **Consumers.** Migrate `util/api.util.ts` and the other utils from `process.env.X` to `Config` lookups, one util per commit. Run `npm run typecheck` after each, and after the API utils run the backend smokes in section 5. Leave specs and page objects on `process.env` (the legacy keys keep working).
6. **Legacy keys.** When no util reads a legacy key any more, stop writing it only if no spec, page object, workflow or external tool reads it either. Keep the keys external tools read (Allure `environment.properties`, workflow steps, Teams notifications, `scripts/triage/verdict.js`, `run-po-backend-batches-parallel.js`) and list them in the PR.

## 8. Risks and rollback
- **A missed combination changes a URL in CI.** The parity script covers every combination in `setup.js`'s branches. Derive the list by reading its `if` branches, not from memory.
- **STAGE inherits INTEROP values.** STAGE shares the interop Gravitee domain, and `.env`/CI often carries INTEROP settings. The parity runs with INTEROP-style overrides set must show STAGE ignoring them.
- **Per-test realm switches use stale hosts.** See step 3, runtime realm override.
- **Another environment gets added mid-task** (as STAGE was in PR #711). Rebase, add the row, and re-run parity before merging.
- **Rollback:** `setup.js` is one file; revert it, and the `configs/env` files become unused.
