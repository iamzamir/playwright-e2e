## 1. Problem
After T3.1, a passing test with a failed `compareTwoValues` check gets an `unasserted-check` annotation (`PW_UNASSERTED_CHECKS=warn`). Each one is a check that was meant to count and doesn't. Switching to `fail` before these are sorted would turn tests red for reasons nobody has looked at.

The original plan rolled this out over four waves, with 3 nights per wave. Measuring nightly results showed the problem is too small to need that (section 2), so this task fixes the known causes and then changes the default once.

**Findings from slice 1 (2026-11-06):**
- Cause 2 is not a defect. `createdTimestamp` shows validation started moments earlier and is still running when the 10 × 3 s poll ends; one TC6 attempt reached `FAILED` after about 80 s. TC2 only needs a status, so its check was fixed and the poll left alone.
- Cause 3 is still open. On 2026-11-04 the success toast arrived 21–29 s after "procedure is running". On 2026-11-05 both specs missed it for the whole 60 s wait at about the same time, yet the scenario was listed in Manage Scenarios about 6 s later. So it is not a tight wait, but a slow procedure and a toast that never showed look the same, because passing tests keep no network log. Settling it needs a run that captures the network (`PW_NETWORK_ARTIFACT_MODE=always`) on a night the toast is missed. Until then the check stays as it is, so it keeps showing as `unasserted-check`.

Limits: three nights only catches mismatches that happened in those runs, and failed or skipped tests are not counted. A different environment or data state could show more, which is why slice 2 watches nights in `warn` first.

Do not count every failed step: passing tests also had 2,236 `[FAIL]` steps that are not `compareTwoValues` checks, mostly API tests that expect an error. Those never reach the ledger.

## 3. Scope
- **In:** the 4 causes above, anything new that `warn` surfaces, and changing the default to `fail`.
- **Out:** the static list of call sites (T3.3), per-workflow waves.

## 4. Implementation steps
**Slice 1: fix the known causes**
1. Fix causes 1, 2 and 4 as in section 2.
2. Investigate cause 3 using the healer procedure, then apply the outcome. Do not move it to `valuesMatch` just to get green; a toast the user should see is a real check.
3. Run each changed spec in isolation with `PW_UNASSERTED_CHECKS=fail`.

**Slice 2: make `fail` the default**
4. With T3.1 and slice 1 merged, read `unasserted-check` and `hook-failed-check` annotations from 3 nights, across all suites. Count a `beforeAll` check once: its annotation repeats on every test in its scope. `fail` does not enforce `hook-failed-check`, so give any that matter an `expect` in the hook.
5. Sort each new entry:
   - Missing from the final assertion → add the boolean to the test's final `expect`.
   - Probe, where `false` is a normal answer → `valuesMatch`.
   - Log-only step → `logMessage`.
   - Real mismatch → known issue with a Jira key (`role-sdet-architect` drafts it from the evidence), or a test data fix.
6. Change the default in `getUnassertedChecksMode` (`util/common.util.ts`) from `warn` to `fail`. Update the `playwright-e2e/README.md` env-var table and the self-test for an empty mode. `PW_UNASSERTED_CHECKS=off` stays as the emergency switch.
7. If step 4 shows more than a handful of new causes, stop and tell the user before changing the default; a staged rollout may be needed after all.
