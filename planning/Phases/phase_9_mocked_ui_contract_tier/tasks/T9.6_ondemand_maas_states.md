## 1. Problem
The ODM specs need the MaaS cluster in a given state ("Inprogress", "Started", "Error", "stopped") at the moment the test looks. On a shared INTEROP cluster that is luck, so 003 and 008 fail every night, and 004 and 007 spend minutes waiting for state changes. The UI part (status chip, "more details" popup, troubleshoot link, unified empty and error screens) can be tested against synthetic states. The cluster part can't, and it keeps one real check.

## 4. Implementation steps
1. Record one HAR for a real run of `Test_004` TC1–TC3 (the cluster in Started state), with the URL pattern limited to the planning-instance and status endpoints found in T9.2.
2. Write mocked specs:
   - **Status:** use `mockFromHar` to turn the recorded Started response into Inprogress, Started, Error and Stopped. Assert the chip text, the "more details" fields (instance id, run id) and the troubleshoot link for each.
   - **Hierarchy filter and another view:** assert the status request carries the filter, then the chip.
   - **Unified error and empty:** use `mockFromHar` (error state) or the empty view filter list. Assert the `loaders-empty-states.component.ts` texts and actions.
   - **Filter not configured:** use an empty filter config response, and assert the toast.
3. Keep in the real `Test_004` only TC1 and TC2 (the real cluster reaches Started after DataSetup). Delete the rest from `Test_004` and `Test_007`, and remove the real `Test_003` and `Test_008`. Note in the PR body which mocked test replaces each removed one.
4. Registration: the mocked specs go in `PSMockedBatch.json`, and `OnDemandMaasBatch.json` is updated. Regenerate the test-case docs.
