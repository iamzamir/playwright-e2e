## 1. Problem
The visual suite has never been stable. Of the last 10 runs in the run-78 history trend, each had 5 to 10 of its 13 tests fail. None of the failures were rendering regressions. The screens show live, shared INTEROP data and per-user state that other workflows change while the suite runs (the PS UI nightly starts at 22:00 UTC and the visual suite at 22:15, with the same `TEST_AUTOMATION_USER_1/2`). A red visual run therefore tells us nothing, and a real layout or CSS regression gets lost among those failures.

The goal is for the screenshot to depend only on the deployed UI bundle. Data, user state and shell noise are fixed, so any diff that remains means the UI changed.

## 3. Scope
- **In:** all 13 specs in `CompleteSmokeVisual`. The 6 failing specs come first; the 7 passing ones follow so the whole suite is deterministic.
- **In:** a default "stable shell" for every visual capture (header badge, avatar and date-like regions masked or stubbed).
- **Out:** the real E2E tests for view mapping, hidden views and view settings (`ViewsBatch`, PO UI suites). They stay live. This task mocks only the *visual copies*, which check how things look, not that the data is right.
- **Out:** MFE or portal component tests (T9.9).

> **Phase 9 rule check.** The phase README lists "Views mapping, hidden views and view settings" as *not* candidates for mocking. That rule protects functional coverage, and the functional specs above keep it. The visual specs were created as copies of those functional tests (see the `// Source:` comment in each spec). They add no data coverage of their own, so mocking them removes no real E2E check. The reviewer confirms this per spec (section 7).

## 4. Implementation steps

### Step 1: Map the calls behind each screen (no code change)
For each of the 13 specs, run once locally with `NetworkInterceptor` (or `PW_HAR_MODE=record` and a wide `guard`). List the data endpoints that decide what the screen shows, and add the list here. Expected groups, to confirm:
- PO Global Settings: planning views list, view groups, process list, process-to-view mapping, arrange-views map-with.
- PS: views/hidden-views lists, view definition (view settings), owner/users lookup, `GET /lui/uiConfiguration/v1/preferences` (last filter, `vfData`), `POST simulations/search` (scenario chip).
- Shell: notifications count, user profile (avatar initials), anything else in the header.

### Step 2: Visual harness: deterministic capture (`util/visual-helper.util.ts`, `configs/fixtures.ts`)
1. A `stableShell` default for `validatePage`: mask the portal header's notification badge and the region of the sparkle/assistant icon. Alternatively, stub the notifications-count call with `mockJson` to return 0. Prefer the stub: a mask hides layout changes as well.
2. Inject a capture stylesheet before every screenshot: no animations or transitions, `caret-color: transparent`, hidden scrollbars (the run-78 PO diff includes a scrollbar shift). Playwright's `animations: 'disabled'` and `caret: 'hide'` cover part of this.
3. Add a `visual.useMockedData({ area, name, url, guard })` helper, a thin wrapper over `useApiHar` + `finishApiHar` + `trackApiHarResult`, so a spec declares its HAR in one line and gets the record/replay switch.
4. Pin per-user state that the screen reads at load. Navigate straight to the process or view by URL instead of relying on last-accessed. Set the `RECENT_ENTITIES_*` localStorage key with `addInitScript`. Answer `preferences` from the HAR. Apply `pinDefaultScenario` where the bottom bar shows a scenario.

### Step 3: Pilot (PO `Test_003_PlanningViewsSettings`, the noisiest)
1. Before INTEROP is changed by other runs, record the HAR from a known state: `PW_HAR_MODE=record VISUAL_SUITE=<pilot-only suite>`. Save it to `testdata/INTEROP/har/Visual/PO-Settings-PlanningViews.har` and check that redaction passed.
2. Regenerate that spec's baseline **on the CI runner image** (`workflow_dispatch` with an update flag, or the Playwright Docker image that matches the Ubuntu runner), not on Windows, so font rendering matches CI.
3. Prove it: 3 replay runs in a row green with diff 0. With `VISUAL_FORCE_DIFF=true` it fails. A deliberate one-line CSS change (an injected style) also fails.

### Step 4: Migrate the other five failing specs
In order: PO 001, PO 002, PS 004, PS 002, PS 003. One HAR per spec file, given the IndexedDB cache rule. Wherever the screen allows, switch from `validatePage` to `validateArea` on the MFE content (the panel or grid) and let one separate spec own the shell header.

### Step 5: Bring the passing specs in line
- 005–009: these depend on dedicated INTEROP processes staying in a fault state. Move them to synthetic `mockJson` / `mockStatus` states, in coordination with T9.8, which covers the same states functionally. Then they stop depending on `testervalue` and similar data.
- 001 and 011: add the HAR or stable shell only if Step 1 shows live data in the frame.

### Step 6: Suite and CI wiring
- Keep `CompleteSmokeVisual.json` as the entry point. Add `PW_HAR_MODE` handling to `.github/workflows/visual-automation-test.yaml` (replay by default).
- Because replay needs no live data, the visual suite can join `pr-checks.yaml` once D7 is answered (same gate as T9.3). Until then it stays nightly.
- Move the visual cron away from the PS UI nightly window, or make the specs independent of it (they will be after Step 4).
- Hook the HARs into T9.4's weekly refresh. When the drift report flags a changed response for a visual HAR, the same PR re-baselines that screen and shows the image diff in the PR.

### Step 7: Docs and skill
Update the `visual-regression-baselines` skill. Every new visual spec uses `useMockedData` plus a CI-generated baseline. Add the "investigate a diff" path for HAR drift versus UI change. Regenerate `docs/testcases`.

## 8. Risks and rollback
- **Mocks hide a real data-rendering bug** → the live functional specs and one live visual shell spec stay in the nightly. Mocks fix only the inputs, never the bundle.
- **The MFE response contract changes and the replay goes stale** → `notFound: 'abort'` plus `guard` makes the spec fail loudly instead of falling back to live data. T9.4's weekly refresh shows the drift.
- **A header (shell) change, such as the new sparkle icon, is a real product change** → one dedicated live spec for the shell owns it, re-baselined in a reviewed PR. The other specs don't fail on it.
- **Linux and Windows render differently** → baselines come only from CI or Docker.

Rollback: drop `useMockedData` from a spec and restore its previous baseline. Each spec moves on its own.
