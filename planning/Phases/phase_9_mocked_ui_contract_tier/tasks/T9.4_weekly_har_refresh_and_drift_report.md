## 1. Problem
A recorded response is a copy of the API on one day. If the backend renames a field or the MFE starts calling a new endpoint, the mocked tests keep passing on the old copy while the real product has changed. That is the main risk of the tier. The HARs need regular re-recording, and someone needs to see the fields that changed rather than a 5,000-line JSON diff.

## 2. Evidence (verified 2026-10-27 on `main` @ `4d5cf28`)
- The T9.1 utility records with `PW_HAR_MODE=record` and redacts in place.
- No workflow opens PRs today. The repo's workflows use `peaceiris/actions-gh-pages` (pinned by SHA since T2.5) for reports only.
- Recording needs the real data to exist. For ScenarioBatch that means the real `Test_003` and `Test_006` must have created their scenarios in the same environment.

## 3. Scope
- **In:**
  - `.github/workflows/har-refresh.yaml`: weekly (Sunday) plus `workflow_dispatch`, INTEROP. It runs `npm run har:record:interop` over `tests/PlanningSpace/Mocked`, then replays once.
  - `scripts/har/drift-report.js`: for each changed HAR, list per endpoint the JSON paths that were added, removed or changed type. Values are not compared, because data changes every week.
  - A PR via `gh pr create` with the report in the body, plus a Teams message if any path was *removed* or changed type.
- **Out:** comparing against an OpenAPI spec (the backend repos don't publish one for these endpoints today; revisit when they do).

## 4. Implementation steps
1. **`scripts/har/drift-report.js`** (plain Node, `node --test` unit tests in `scripts/tests/`):
   - Load the old HAR (`git show HEAD:<path>`) and the new one.
   - Group entries by method plus URL path without the query.
   - Flatten JSON bodies to a `path → type` map, with arrays collapsed to `[]`.
   - Output a Markdown table: endpoint | added | removed | type changed.
   - Exit 0 always. The workflow decides what to do with the result.
2. **Workflow:**
   - Check out a new branch `har-refresh/<date>`.
   - Run the real seeding specs first (ScenarioBatch `Test_003` and `Test_006` TC1–TC2 through `SPECIFIC_TESTS`).
   - Record, then replay once with `PW_RETRIES=0`. If the replay fails, the recording is bad: fail the job and open no PR.
   - Run the secret grep from T9.1 section 5.
   - Run the drift report, commit, push and `gh pr create`.
   - Use the repo's existing bot token pattern, with `contents: write` and `pull-requests: write` only.
3. **PR body:** the drift table, the HAR size change, and a reminder that a removed or retyped path means checking the real E2E test for that feature before merge.
4. **Teams message** (reuse the existing Teams step) only when the "removed" or "type changed" columns aren't empty.

## 5. Verification
```bash
cd playwright-e2e
node --test scripts/tests/har-drift-report.test.js
gh workflow run har-refresh.yaml --ref ci/har-weekly-refresh
gh run watch && gh pr list --search "har-refresh"
```
Expected:
- The unit tests pass.
- The dispatch opens one PR whose body has the drift table.
- Removing a field by hand from the old HAR in a test commit shows that field under "removed".

## 6. Acceptance criteria
- [ ] The weekly workflow records, replays, checks for secrets, reports drift, and opens a PR. A replay failure stops it.
- [ ] The drift report lists path and type changes only, and has unit tests.
- [ ] Removed or retyped fields send a Teams message.
- [ ] Two scheduled refresh PRs have been opened (the phase exit criterion; tick after two Sundays).

## 7. Review checklist (for `role-sdet-architect`)
- [ ] The workflow token scopes are minimal, and the job can't push to `main`.
- [ ] The secret grep runs *before* the commit.
- [ ] Seeding specs run before recording, so a missing scenario doesn't record an empty list.

## 8. Risks and rollback
- **INTEROP data is in a bad state on Sunday** → the replay check fails and no PR is opened. The old HARs stay.
- **Noise from data-only changes** → the report compares types, not values.

Rollback: disable the workflow. The HARs stay valid until the API changes.
