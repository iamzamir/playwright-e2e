## 1. Problem
The repo can't run a UI test against recorded API data. Every Planning Space test depends on live, shared INTEROP data, so a filter test fails when the data it needs isn't there, and a 15-test filter file takes 7 minutes. Before migrating ~90 tests, one utility and one pilot spec have to show that record, redact and replay work through the portal relay and the cached browser context.

## 4. Implementation steps
1. **`util/har.util.ts`.**
   - `useApiHar(context, { area, name, url })` sets `routeFromHAR` on the context.
     - Replay mode (default): `notFound: 'abort'`. It throws with the record command if the file is missing.
     - Record mode (`PW_HAR_MODE=record`): `update: true`, `updateContent: 'embed'`, `updateMode: 'minimal'`. It creates the folder.
   - `finishApiHar(context, handle)` does nothing in replay mode. In record mode it closes the context (this writes the HAR), then redacts the file in place.
   - `redactHar(har)` does three things:
     - It drops `SENSITIVE_HEADERS` from requests and responses, and empties `cookies`.
     - It runs `redactApiText` over response bodies, decoding `base64` text bodies first.
     - It leaves request URLs and `postData` untouched, because replay matches on them.
   - The redacted HAR is checked for a JWT or `Bearer <token>`. If one is found, `finishApiHar` throws and never writes it.
   - `findSensitiveRequestData(har)`: request URLs and bodies can't be redacted (replay matches on them), so recording fails if the `redactApiText` rules would change any of them (tokens, `access_token=`/`code=` params, secret-named keys, emails).
   - Optional `guard` (a wider pattern, for example `**/simulations/**`), replay only: a request that matches it but not `url` is aborted and `finishApiHar` fails, so a renamed endpoint can't fall through to live data. It isn't installed in record mode, because there `routeFromHAR` passes recorded requests on to the next route.
2. **Export** `SENSITIVE_HEADERS` from `util/api-calls.util.ts` (no other change there).
3. **Pilot spec** `tests/PlanningSpace/Mocked/ScenarioBatch/Test_003_ScenarioVisibilityFilterMocked.spec.ts`:
   - Same two contexts (Process, Subprocess) and the same `applyVisibilityFilter` check as the real spec.
   - `beforeAll` installs the HAR on `page.context()` **before** `launchAppFromCatalog`, so the first scenario search is already served from it. `afterAll` calls `finishApiHar`.
   - Per context:
     - TC1 opens Manage Scenarios and resets the filters. It asserts that the recorded private and public scenarios are listed.
     - TC2–TC4 apply Private, Public and All. Each one asserts the *request* (`visibility` key sent for Private and Public, none for All) and the *rendered* Visibility column.
   - There are no create steps: the scenarios come from the recording. The real spec keeps creating them (and is the "keep real" test for this feature).
   - Use the `scenarioPage` page object methods only, and no new locators. The request check uses `page.waitForRequest`, which is not a locator.
4. **Test data:** `testdata/INTEROP/PlanningSpace/Mocked/ScenarioBatch/Test_003_ScenarioVisibilityFilterMocked.json`, with the same fields and `_schema` as the real spec's file, plus `HAR_AREA` and `HAR_NAME`.
5. **Record the HAR** on INTEROP once the real `Test_003` has created the scenarios in both contexts.
   ```bash
   cd playwright-e2e
   npm run har:record:interop -- tests/PlanningSpace/Mocked/ScenarioBatch
   ```

   - `har:record:interop` runs the given paths with `PW_HAR_MODE=record`, `--workers=1` and `PW_RETRIES=0`.

## 7. Review checklist (for `role-sdet-architect`)
- [ ] The URL pattern is no wider than the API the spec needs (no IAM, no CDN, no `**/*`), and a `guard` covers the rest of that API resource.
- [ ] Replay uses `notFound: 'abort'`. No test can quietly pass on live data.
- [ ] The HAR is installed before the first navigation that triggers the call.
- [ ] Record mode closes the context, and replay mode doesn't, so the cached page keeps working for the rest of the file.
- [ ] The spec asserts what the UI sent as well as what it showed. A mocked test that only reads back the mock is worthless.
- [ ] No inline locators, no sleeps, and timeouts from `getTimeout`.

## 8. Risks and rollback
- **The portal rewrites the relay URL, so the pattern doesn't match** → the replay check in section 5 step 4 catches it. Widen to the gateway host plus path, never to `**/*`.
- **The MFE adds a timestamp or a random id to the search URL** → replay aborts and the test fails clearly. Then match with a `url` predicate in a hand-written `context.route` that ignores that parameter, and record that in the learnings.
- **The recorded scenarios get deleted on INTEROP** → doesn't matter for replay. The next refresh (T9.4) needs the real `Test_003` to have run first.
- **HAR size** → `updateMode: 'minimal'`, one area per file. If a HAR is over 5 MB, split it by context.

Rollback: delete the new spec, test data, HAR, suite JSON and npm scripts, and revert the one-word export in `api-calls.util.ts`. Nothing else uses them.
