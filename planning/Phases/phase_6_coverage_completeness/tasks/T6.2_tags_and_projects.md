## 1. Problem
Run selection is spread across JSON globs, folder scripts and `TEST_IGNORE`. Whether to run the browser login global setup is decided by searching for the text "backend" in suite names and spec paths. Adding a backend spec with a different folder name, or a UI suite named "...Backend...", silently changes the auth behaviour.

## 2. Evidence (verified 2026-10-08 on `main` @ `f3d48bb`)
- `configs/playwright.config.ts:54-76` `shouldEnableGlobalSetup()`: `PW_ENABLE_GLOBAL_SETUP=false` → off; suite name contains `backend` → off; spec text contains `processorchestrationbackend` → off; …
- API specs import from `configs/api-fixtures`; UI specs from `configs/fixtures`.
- Playwright 1.52 supports `test.describe('...', { tag: ['@ps', '@smoke'] }, ...)` and `--grep @tag`.

Re-check:
```bash
cd playwright-e2e
sed -n 54,80p configs/playwright.config.ts
grep -rl "configs/api-fixtures" tests | xargs -n1 dirname | sort -u
```

## 3. Scope
- **In:** a tag vocabulary; tags added to every spec; `projects` in `playwright.config.ts` (`api`, `ui` with a `setup` dependency); removing `shouldEnableGlobalSetup`; the npm scripts and workflow commands that need `--project`.
- **Out:** replacing the suite JSONs entirely. They keep the shard and batch grouping; tags and projects decide auth and cross-cutting selection (`@smoke`, `@destructive`). Revisit after one month.

## 4. Implementation steps
1. **Vocabulary**, documented in `playwright-specs.instructions.md`:
   - **Execution type** (exactly one per spec; this decides the project): `@api` or `@ui`.
   - Area (reporting and selection only, never used to pick a project): `@ps`, `@po-ui`, `@po-backend`, `@datasetup`, `@visual`, `@perf`.
   - Purpose: `@smoke`, `@destructive` (all of DataSetupBatch), `@manual-only`.
   - Environment: `@env-qa`, `@env-psr` where the spec is meant to run there (INTEROP is the default; see T6.3).
   Area and execution type are different things. For example, `DataSetupBatch/Scenarios/Test_002_SetBaseScenarioAsDefault.spec.ts` is `@datasetup` but imports `configs/fixtures` and drives Planning Space with `page`, so it's `@ui`. On 2026-10-08, 18 DataSetup specs import `configs/api-fixtures` and that 1 imports `configs/fixtures`.
2. **Add tags** to every top-level `test.describe` with a script (`scripts/add-area-tags.js`, run once and committed for traceability):
   - **Execution type from the fixture import:** `configs/api-fixtures` → `@api`; `configs/fixtures` → `@ui`. A spec importing neither (for example the Performance specs, which import `@playwright/test` and launch `chromium` themselves) is reported by the script for a manual decision; don't guess.
   - Area from the folder, `@destructive` for DataSetupBatch, and `@smoke` for specs in `PSSmokeBatch.json` and `POBackendSmokeBatch.json`.
   - Review the diff by sampling; the script must be idempotent.
3. **Projects** in `configs/playwright.config.ts`, split on the execution tags only:
   ```ts
   projects: [
     { name: 'setup', testMatch: /global\.setup\.ts/ },           // only if global-setup becomes a setup project; otherwise keep globalSetup and gate it per project (see below)
     { name: 'api', testMatch: testSpecs, grep: /@api\b/, use: { /* no browser-specific options */ } },
     { name: 'ui', testMatch: testSpecs, grep: /@ui\b/, dependencies: ['setup'], use: { /* current browser options */ } },
   ]
   ```
   - Using `grep` on both projects (not `grepInvert` on one) means a spec with no execution tag lands in **no** project, and the `--list` comparison in step 6 shows it as missing instead of letting it run with the wrong setup.
   - Add a validator check (T2.3 script): every spec has exactly one of `@api` / `@ui`, and it matches its fixture import.
   - Read `configs/global-setup.ts` first. It caches storage state for UI users. If converting it to a setup project is too large a change, keep `globalSetup`, and make it skip when every selected test is in the `api` project (`--project=api`). The goal is to remove the text matching, not necessarily to convert.
   - The `DataSetupBatch` guard from T1.2 stays (config-level `testIgnore`); the `@destructive` tag adds `--grep-invert @destructive` as a second layer in scripts.
4. **Scripts and workflows:** backend scripts add `--project=api`; UI scripts `--project=ui`. The DataSetup job keeps both projects (no `--project`), because its suite mixes `@api` specs with the `@ui` `Test_002_SetBaseScenarioAsDefault`. Update the PO backend, PO UI, PS UI and custom workflows' commands. Remove `PW_ENABLE_GLOBAL_SETUP` from places where the project now decides (keep the env var as a manual override).
5. Delete `shouldEnableGlobalSetup()`.
6. Check `--list` counts per suite before and after: they must be identical.
