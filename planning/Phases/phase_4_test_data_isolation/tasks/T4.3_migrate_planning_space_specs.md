## 1. Problem
Only 26 of 126 Planning Space specs clean up after themselves. The ones that create scenarios, filters, views and supply chain actions leave data that later specs trip over, and that the nightly bulk delete has to remove.

Kick-off re-check 2026-11-02 on `main` @ `c8b23d4` (after T4.1 and T4.2):
- T4.1 replaced every `Math.random` name with `uniqueName`, so that column is now 0 everywhere; use `uniqueName(` counts instead.

Five specs create per-run scenarios (`Test_001`, `002`, `004`, `007`, `009`); four ensure fixed, seeded scenarios exist (`003`, `005`, `006`, `014`); `Test_008` is skipped; the rest only read.
- Scenarios are user-owned, so the deleter needs the user's token. The existing API cleanup that passes in CI uses the token captured from the UI; the scenario search also works with the scoped machine token (`getBearerToken()`), but `buildAuthHeaders()` (no scope, the deleter's fallback) is unproven on the Azure gateway. Specs therefore register scenarios with the Authorization and body of the UI's own `simulations/search` request (`BasePage.trackApiRequests` + `registerScenario` in `util/scenario-cleanup.util.ts`), which also gives the right `sourceIds` for Subprocess and Assumption contexts.
- User tokens can expire before worker teardown on a long folder run, so migrated specs also call `createdEntities.cleanupFile()` in `afterAll`.

## 3. Scope
- **In:** for each folder, registering every created entity with `createdEntities`, replacing hand-written cleanup that the fixture now covers, and fixed names → `uniqueName` (if T4.1 missed any).
- **Out:** test logic changes; splitting `describe.serial` blocks (record candidates instead).

## 4. Implementation steps (repeat per folder, one PR each)
1. **Inventory.** For each spec in the folder, list what it creates (entity kind, how the name is built, which test case creates it, whether it's cleaned up today). Put the table in the PR description.
2. **Register.** Right before the create or save is submitted (see the review checklist in section 7 for why):
   ```ts
   createdEntities.register('scenario', name, { context: { process: testData.PROCESS_NAME } });
   await scenarioPage.createScenario(name);
   ```
   - Add `createdEntities` to the test's fixture parameters.
   - If the UI flow doesn't expose the id, register by name and context. The deleter resolves the id through the API.
3. **Remove redundant cleanup.** Delete manual `afterAll` cleanup that only deletes registered entities. Keep cleanup that *restores* state (for example resetting a default scenario or a toggle). That's not deletion, and the fixture doesn't do it.
4. **Specs that intentionally use fixed, pre-existing data** (for example a seeded view they only read): no change. Note them as "reads seeded data" in the inventory.
5. **Run the folder:**
   ```bash
   cd playwright-e2e
   cross-env ENVIRONMENT=INTEROP TZ=Australia/Adelaide USE_SPECIFIC_TESTS=false npx playwright test tests/PlanningSpace/<Folder> --config=configs/playwright.config.ts --workers=1
   ```
   Then check the environment through the API or UI: none of the run's `uniqueName` entities remain (search by the run id).
6. Run it a second time immediately. It must pass without the bulk DataSetup in between.
7. Update the phase exception table (in T4.5's file) with any spec that can't register its data, and why.

## 7. Review checklist (for `role-sdet-architect`)
- [ ] Registration happens before the create or save is submitted, with the run's `uniqueName`, so a create that succeeds while its success toast is missed still gets cleaned up. Deleting an entity that was never created is a not-found no-op, so it doesn't count as a failure. *(Changed 2026-11-11 from "after the create succeeded, not before" to match the merged practice in #952 and #987, accepted in this task's 2026-11-02 review.)*
- [ ] State-restoring cleanup was kept.
- [ ] No test assertions changed.

## 8. Risks and rollback
- The fixture deletes data another spec in the same worker still needs (shared data across files) → worker teardown runs after the worker's last file. If a later file depends on an earlier file's data, record that as a test-design defect in the PR, and don't migrate those two specs until it's fixed.
- Rollback: revert the folder's PR.

## 9. Docs and learnings
- Learnings: per-folder quirks (for example, a scenario can't be deleted while it's the default).
