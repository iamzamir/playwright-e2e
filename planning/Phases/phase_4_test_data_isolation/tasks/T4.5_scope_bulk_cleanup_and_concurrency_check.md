## 1. Problem
The nightly DataSetup specs delete broadly (some everything of a kind, some by loose patterns), so they can remove another team's data or another run's in-flight data. Once specs clean up after themselves (T4.3, T4.4), DataSetup only needs to sweep automation leftovers, identified by the `uniqueName` pattern and older than a safe age.

## 3. Scope
- **In:** for each DataSetup delete spec: restrict deletion to automation-pattern names older than `PW_CLEANUP_MIN_AGE_HOURS` (default 6), log what's kept and deleted, and add a dry-run mode everywhere. Then a concurrency proof and the phase exception table.
- **Out:** the migration-target `DeleteAll*` specs. They reset a dedicated target realm on purpose; keep them behind T1.2's guard (D5), and only add dry-run and logging.

## 4. Implementation steps
1. **Shared filter** `util/cleanup-filter.util.ts`:
   ```ts
   export type CleanupDecision = { delete: boolean; reason: 'not-automation' | 'too-new' | 'unknown-age' | 'leftover' };
   export function decideCleanup(name: string, createdAt?: string, minAgeHours = Number(process.env.PW_CLEANUP_MIN_AGE_HOURS || 6), now = Date.now()): CleanupDecision
   ```
   Rules, in order:
   1. The name matches neither `AUTOMATION_NAME_PATTERN` nor the legacy prefix list (one place, documented) → keep, `not-automation`.
   2. **Age:** take `createdAt` from the API if it parses as a valid date. Otherwise, for `uniqueName` names, take the creation time encoded in the name (`parseUniqueName(name).createdAt`, from T4.1). If neither gives a valid time → keep, `unknown-age`. **A missing or invalid timestamp never counts as old**, because an in-flight entity from another run can look exactly like a leftover.
   3. Younger than `minAgeHours` (or a timestamp in the future) → keep, `too-new`.
   4. Otherwise → delete, `leftover`.
   - Legacy prefix list: collect it from the specs' current filters and from the prefixes T4.1 kept. It's needed until old leftovers age out; set a removal date (30 days after merge) in a code comment and in the progress log. Legacy names carry no timestamp, so they're deleted only when the API returns `createdAt`. Entities kept as `unknown-age` are listed in the DataSetup log for a person to review.
   - Unit tests (`node:test` or a `tests/_framework/` spec) must cover each rule, including: `createdAt` missing, unparseable, or in the future; a `uniqueName` name without `createdAt` (age taken from the name); and a legacy name without `createdAt` (kept).
2. **Apply** the filter in each non-target DataSetup delete spec. Log one count per reason: `kept: N (not automation)`, `kept: N (too new)`, `kept: N (unknown age)`, `deleted: N`.
3. **Dry run everywhere:** `PW_CLEANUP_DRY_RUN=true` lists without deleting (reuse the existing `dryRun` pattern in `Test_001_DeleteProcesses` and `Test_005_CleanupDuplicateViews`).
4. **First run in dry-run mode on INTEROP** (with the user's OK; this lists shared data). Compare "would delete" with today's behaviour. Anything that today's run deletes and the new filter keeps must be explained (another team's data, or a legacy prefix you missed).
5. **Concurrency proof.** Dispatch the PS UI workflow twice, a few minutes apart, on the same suite (for example `ScenarioBatchA`), without DataSetup (ask the user first; it doubles the load on INTEROP). Compare both runs' failures with a single run from the same day: no new failure may mention another run's data.
6. **Exception table.** Add to this file's section 9 every spec that can't clean up its own data, with the reason and the leftover it creates.

## 8. Risks and rollback
- Old leftovers without the new pattern pile up → the legacy prefix list covers them for 30 days.
- The filter is too strict and data accumulates → the DataSetup log shows `kept` counts nightly; watch them for a week.
- Rollback: revert; the old broad deletes come back.
