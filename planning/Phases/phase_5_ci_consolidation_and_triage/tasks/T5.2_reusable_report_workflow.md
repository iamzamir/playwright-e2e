## 1. Problem
The `generate-report` job is several hundred lines in each workflow (for example `playwright-ps-iop-ui-local-suite.yaml:414-817`). It downloads the shard results, restores Allure history from gh-pages, copies `categories.json`, runs the triage enrichment, verdict and run data, generates Allure, pushes to gh-pages (latest plus numbered builds), publishes dashboard data, and posts the Teams card. The functional workflows have grown near-identical copies, and the visual and performance workflows have older, different ones.

## 2. Evidence (verified 2026-10-08 on `main` @ `f3d48bb`)
- PS UI `generate-report`: lines 414-817; `run-verdict`: 830-870. PO UI and PO backend have the same structure.
- Visual `generate-report`: `visual-automation-test.yaml:184-458`; performance: `playwright-performance.yaml:303-587`.
- Already reusable: `github-pages-deploy.yaml` (`on: workflow_call`), called after the gh-pages push.
- Learnings "CI/CD and GitHub Actions" describe the history restore (`latest/history` → `allure-results/history`), the `latest` purge, the run data path `dashboard/data/runs/<date>/<suite>__<run>.json`, and `triage/categories.json` copying. The reusable workflow must keep all of that.

## 3. Scope
- **In:** `.github/workflows/_report.yaml` (`workflow_call`) with jobs `generate-report`, `deploy-pages` (calls the existing `github-pages-deploy.yaml`) and `run-verdict`; adopting it in **one** functional workflow (PS UI) as the pilot.
- **Out:** the other workflows (T5.3).

## 4. Implementation steps
1. **Diff** the `generate-report` jobs of PS UI, PO UI and PO backend step by step. Make a table: step, identical or different, the parameter that captures the difference (suite key, artifact pattern, report folder, environment and gateway labels, Teams title).
2. **Inputs** for `_report.yaml`:
   `suite-key` (gh-pages folder, for example `PW-PS-UI-INTEROP-LOCAL`), `results-artifact-pattern` (for example `allure-results-*`), `merge-multiple` (bool), `report-title`, `environment`, `gateway` (optional), `verdict-mode-var` (name of the repo variable, default `PW_VERDICT_MODE`), `check-count` (bool), `upstream-result` (the caller's test job result), `teams-enabled` (bool), `runner` (label).
   **Secrets:** `inherit` from the caller, so no secret names are duplicated.
   **Outputs:** `verdict`, `red`, `headline`, `report-url`.
3. **Move** the PS UI `generate-report` steps into `_report.yaml` with inputs substituted. Keep step names identical, so the Actions UI and log searches still match.
4. **Pilot:** in `playwright-ps-iop-ui-local-suite.yaml`, replace `generate-report`, `deploy-pages` and `run-verdict` with:
   ```yaml
   report:
     needs: [run-tests]
     if: always()
     uses: ./.github/workflows/_report.yaml
     with: { suite-key: PW-PS-UI-INTEROP-LOCAL, results-artifact-pattern: 'allure-results-*', merge-multiple: true, report-title: 'PS UI · INTEROP', environment: INTEROP, upstream-result: '${{ needs.run-tests.result }}', check-count: true, teams-enabled: true, runner: az-dev-ubuntu-latest-8Core }
     secrets: inherit
   ```
5. **`nightly-triage.yaml`** matches workflow runs by the caller's `name:` (learnings). A reusable workflow doesn't change the caller's name, but check that the run data file name and path are unchanged.
6. **Compare:** dispatch PS UI on the branch for one small batch (with the user's OK; it publishes to gh-pages and Teams). Compare with the last `main` run: the gh-pages folder layout, the Allure history trend present, the dashboard run-data file present and the same shape (`jq 'keys'`), the verdict summary, and the Teams card.
