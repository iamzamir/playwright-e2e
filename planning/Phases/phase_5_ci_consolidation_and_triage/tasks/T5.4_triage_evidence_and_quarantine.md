## 3. Scope
- **In:** (a) E7: record UI and service versions per run in run data; (b) E8: a health probe step before tests, with results in run data and verdict BROKEN/ENV when it fails; (c) quarantine: tag and run quarantined tests in a separate nightly job and keep them out of the main verdict. Each is a separate PR.
- **Out:** change correlation and dashboard pages 7/8 (follow-up task if wanted); AI assist (triage Phase 5).

## 4. Implementation steps
1. **Read** triage plan §6 (evidence capture) and §7 (engine) for the agreed design of E7 and E8 before coding. Where the plan and the code differ, the code wins; update the plan.
2. **E7, versions:** find where each UI exposes its version (for example a `/version` or `/health` endpoint, or a build id in page HTML or a response header). Check with the sibling repos in `C:\Backend\<repo>` per learnings. Add `scripts/triage/collect-versions.js` that reads the endpoints with the run's token and writes `reports/triage/versions.json`. `build-run-data.js` copies it into the run data. Unit tests with fixtures.
3. **E8, health probe:** `scripts/triage/env-health.js` probes the key endpoints per environment (login, the PO and LM gateways, planning-mfe), with 2 retries and a 10 s timeout each. It writes `reports/triage/env-health.json` and sets a step output `healthy`. In the workflow it runs before tests with `continue-on-error: true`. `verdict.js` reports BROKEN with reason "environment unhealthy before tests" when `healthy=false`. Unit tests.
4. **Quarantine:** in the functional workflows, run quarantined tests in a separate job (`--grep` on the selectors from `quarantine.json`, or a generated file list) and exclude them from the main run (`--grep-invert`). Publish their results to a separate gh-pages folder (`<SUITE>-QUARANTINE`). Entries that pass N nights in a row are suggested for release (reuse `findRecoveredKnownIssues` logic).
5. Update triage plan §4.2 "Implementation status" with each part when it merges.
