The Link Management automation is now both deep and broad on the surfaces the UIs use. Fourteen suites (Test_001 – Test_014) cover view‑to‑entity mapping including lm-search/v2, procedure‑to‑view mapping, preset filters, scope and user favourites, with negative, boundary and schema assertions. Every LM route that planning-mfe or lui calls is now exercised. The remaining gaps are the view catalogue, the source-entity lifecycle, entity validation / job and the LM-native export / import contract.

Three gaps still carry the highest business risk and should be closed first: POST /importData (no direct proof that an exported tenant can be re-hydrated, now including SM-33313 reason codes), DELETE /entity/{id} (a cascading delete with no regression net), and POST /validate + GET /job/validation/{task_id} (the asynchronous ALM validation contract; Migration/Test_007 targets the ALM platform API, not these routes).

Spec-vs-implementation drift found during review (resolved 05-Oct-2026). GET /ops/db/state is published in links-oas-spec.yaml and is served by the shared OperationsAPI controller in plan-sop-po-be-commons, not by a controller in this repo. G-18 is closed as out of scope.

5. Proposed test suites — execution order

Order is dependency-driven. Phases 0 and 1 create the catalogue views and source entity that later phases consume, so running out of order will produce false failures. 7. Recommendations (status 05-Oct-2026)

  1. Close the remaining P0 set (42 h). Import round trip (now including SM-33313 reason codes), source-entity cascade delete and the validation job are the places where a silent regression reaches customers with no automated warning. v2 batch search is done (Test_012).
  2. Retire the deprecated surfaces instead of testing them. Removing the eight @Deprecated /tenants and /users operations raises overall coverage from 55% to 70% for zero test spend and shrinks the unaudited admin surface.
  3. Done — OAS drift. GET /ops/db/state is served by plan-sop-po-be-commons. An OAS-vs-controller diff is still worth adding to the build.
  4. Break the hard-coded view-id dependency. Test_012–Test_014 already seed their own data with MappingUtil.mapSingleView; migrate Test_001 – Test_008 the same way. The view-catalogue suite proposed as Test_011 has not landed (Test_011 is now AdminFilterManagement).
  5. Partly done — two-user fixture. Test_011 and Test_013 use getUserBearerToken from util/user-token.util.ts for per-user assertions. Presets and tenant isolation still need a second-user case.
  6. Standardise the “assert deterministic” cases. Several test cases above record behaviour the spec does not pin down (duplicate ids, repeat deletes, unknown enums). Test_009 TC-11 already found one such case. Each should raise a spec-clarification ticket rather than an assertion guessed from current behaviour.
