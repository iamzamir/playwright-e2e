Endpoint-level coverage: 59 of 144 active operations exercised by a test body in at least one environment (15 @Deprecated and 2 @Profile("local") mock routes excluded).

The backend suite now covers Calendar/Cycle completely, node attributes, supply chain actions, process search, context and scope, the process and subprocess read APIs, action-item search and Export/Import migration. The orchestration core is still unautomated: transitions, node scheduling and reschedule, event actions, subprocess start/stop, templates, quota and RBAC propagation. These remain the areas with the highest defect blast radius, and lui calls most of them.

Top 5 risks from the gap (updated 05-Oct-2026):
  1. Transition engine (11 endpoints, 1 covered: GET /job/{jobId}/status) — lui calls 7 of the transition routes and none is tested.
  2. Node schedule & reschedule (3 endpoints, 0 covered) — lui calls reschedule; date-cascade defects shift every downstream subprocess.
  3. Event actions (4 endpoints, 0 covered) — supply chain action CRUD is now covered by ProcessBatch/Test_009, but the event bindings that invoke it are not.
  4. Subprocess lifecycle (12 endpoints, 7 covered) — read, update and delete are covered; start/stop (called by lui), referenceable nodes and the subprocess Gantt are not.
  5. RBAC propagation (/users/roles/add|remove) — unchanged; an authorization regression is a security-severity incident, not just a functional one.

5. Test Cases — Execution Order

The service is stateful and hierarchical: a template must exist before a process, a process before a subprocess, a subprocess before a transition, a transition before a meaningful start/stop. The suite below is therefore ordered as a single dependency chain. Each phase produces artefacts consumed by the next; teardown runs in reverse. Run phases sequentially, tests within a phase may run in parallel unless Depends on says otherwise.

Suggested spec layout in the automation repo
e2e/specs/ProcessOrchestrationBackend/<Module>/Test_0NN_<Name>.spec.ts with matching e2e/Testdata/<ENV>/ProcessOrchestrationBackend/<Module>/Test_0NN_<Name>.json, registered in e2e/specs/TestSuites/po-backend-suite.json. New endpoint path variables go into e2e/configs/setup.js alongside the existing CALENDAR / EXPORT_DATA entries.

7. Recommendations

  1. Generate response-schema assertions from the OAS spec. The existing suite only checks status codes and one or two fields. A schema-diff assertion would have caught every contract break in this service for a fraction of the effort.
  2. Fix the tests that encode defects. Calendar/Test_001_CalendarsCRUD still asserts 500 for invalid input in two places. Raise the defect, change the expectation to 400, and add a lint rule that flags any assertion on a 5xx code.
  3. Reuse the shared fixtures. util/process-fixture.util.ts and util/calendar-cycle.util.ts now build calendar → cycle → template → process → subprocess; new transition and event-action specs should build on them.
  4. Standardise async-job polling. Five different flows return a jobId (transition generate, role add/remove, publish, deploy, procedure onboard). One shared poller with a configurable SLA removes flakiness.
  5. Add a negative-path template. For every endpoint assert 400 / 401 / 403 / 404 / 409 explicitly. This is where the current suite is thinnest and where most production incidents originate.
  6. Gate the pipeline on P0 phases only (Phases 5–11). Run P1/P2 phases nightly so PR feedback stays fast.
