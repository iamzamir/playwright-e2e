Playwright E2E Framework — Azure APIM to Gravitee Gateway Migration Architecture & Implementation Plan

Scope: playwright-e2e Setup Files, ProcessOrchestrationBackend Tests, Utility Helpers, & GitHub Actions Workflows

Architecture & Migration Blueprint

1. Executive Summary

This plan defines the technical strategy to update the Playwright E2E automation framework to seamlessly support both Azure APIM Gateway and Gravitee Gateway. By introducing a clean parameterization model driven by a GATEWAY_TYPE parameter (AZURE vs GRAVITEE) and REALM_KEY (e.g. cbpf-test23), the framework can execute backend and UI tests against either gateway without code modifications in test specs.

5. Step-by-Step Implementation Strategy (Baseline — Delivered)

The four steps below form the delivered baseline and are retained for reference. Each is now marked with its verified status against the codebase.

1
Enhance Environment Setup Configuration (configs/setup.js) DONE

Add GATEWAY_TYPE and REALM_KEY processing. When GATEWAY_TYPE === 'GRAVITEE', dynamically construct Base URL, Auth URL, and Portal URL based on active REALM_KEY (e.g. cbpf-test23).

const gatewayType = (process.env.GATEWAY_TYPE || 'AZURE').toUpperCase();
process.env.GATEWAY_TYPE = gatewayType;

if (gatewayType === 'GRAVITEE') {
  const realmKey = process.env.REALM_KEY || 'cbpf-test23';
  const domainSuffix = process.env.GRAVITEE_DOMAIN_SUFFIX || 'interop.na.blueyonder.dev';
  
  process.env.API_BASE_URL = process.env.GRAVITEE_API_BASE_URL || `https://${realmKey}.api.${domainSuffix}/`;
  process.env.AUTH_URL = process.env.GRAVITEE_AUTH_URL || `https://${realmKey}.auth.${domainSuffix}/oauth/token`;
  process.env.LUMINATE_PORTAL_URL = process.env.GRAVITEE_PORTAL_URL || `https://${realmKey}.portal.${domainSuffix}/`;
}
2
Update API Utility Helper (util/api.util.ts) DONE

Refactor getBearerToken() to handle token requests targeting Gravitee's https://${realmKey}.auth.interop.na.blueyonder.dev/oauth/token endpoint.

public async getBearerToken(
  authUrl: string = process.env.AUTH_URL as string,
  clientId: string = process.env.CLIENT_ID as string,
  clientSecret: string = process.env.CLIENT_SECRET as string,
  scope: string = process.env.SCOPE as string,
  realmId: string = process.env.REALM_ID as string
): Promise<string> {
  const isGravitee = (process.env.GATEWAY_TYPE || 'AZURE').toUpperCase() === 'GRAVITEE';
  
  const url = isGravitee ? authUrl : `${authUrl}?realmId=${realmId}`;
  
  const params: Record<string, string> = {
    grant_type: "client_credentials",
    client_id: clientId,
    client_secret: clientSecret,
  };
  
  if (!isGravitee && scope) {
    params.scope = scope;
  }

  const requestData = new URLSearchParams(params);
  const headers = { "Content-Type": "application/x-www-form-urlencoded" };

  const response = await this.processAPIRequest("POST", url, requestData, headers, "Fetching Bearer Token");
  return response.access_token;
}

6. Gap Analysis & Phased Enhancement Plan

The baseline enables Gravitee token acquisition and base-URL routing. The following phases close functional and safety gaps discovered during review. Phases are ordered by risk/impact and can be delivered as independent branches.

P1
Phase 1 — Confirm URL_MODE is gateway-independent CLARIFIED — NO CODE CHANGE

Clarification: URL_MODE and GATEWAY_TYPE are orthogonal axes. URL_MODE=OLD (the default) is the correct and expected mode for both Azure and Gravitee — Gravitee serves the same cbp/{env}/ibp/... OLD-style route shape behind its own base URL. URL_MODE=NEW (po/api/v1/..., ai/api/v1/..., lm/api/v1/...) is a separate migration axis that also applies to both gateways. There is therefore no coupling and no coercion required: any of the four combinations (AZURE+OLD, AZURE+NEW, GRAVITEE+OLD, GRAVITEE+NEW) is valid.

GATEWAY_TYPEURL_MODEResolved Calendar pathValid?
AZUREOLD (default)cbp/interop/ibp/process-orchestration/v1/calendarYES
AZURENEWpo/api/v1/calendarYES
GRAVITEEOLD (default)cbp/interop/ibp/process-orchestration/v1/calendarYES
GRAVITEENEWpo/api/v1/calendarYES

Action: No setup.js change is needed for URL mode — the existing useOldUrls logic already handles both gateways. Do not force URL_MODE=NEW for Gravitee. This phase is documentation-only; it exists to prevent the incorrect assumption that Gravitee mandates NEW routes.

Acceptance: GATEWAY_TYPE=GRAVITEE with the default URL_MODE=OLD resolves against cbp/{env}/ibp/... routes and runs successfully.

P2
Phase 2 — Endpoint routes are gateway-independent (only base URL changes) CLARIFIED — NO CODE CHANGE

Clarification: Every endpoint (including ALM, IAM, foundation-bff, MaaS, simulation, assumptions, and feature-toggle) is a relative path appended to process.env.API_BASE_URL. Gravitee changes only the base URL (https://{realmKey}.api.interop.na.blueyonder.dev/); all relative path segments are identical to Azure. Because the base URL swap already routes those same paths through the Gravitee gateway, no per-endpoint mapping or override is required.

Action: None. The existing API_BASE_URL + <env path segment> composition in every spec already works for Gravitee. Do not add gateway-specific endpoint overrides.

Acceptance: A Gravitee run exercising an ALM/IAM/BFF endpoint resolves against the Gravitee base URL with the same relative path used for Azure.

P3
Phase 3 — Fail-fast validation & QA realm coupling MEDIUM

Gap A (validation): Selecting Gravitee with missing GRAVITEE_CLIENT_ID/GRAVITEE_CLIENT_SECRET silently falls back to Azure credentials and produces confusing 401s.

if (gatewayType === 'GRAVITEE') {
  const missing = ['GRAVITEE_CLIENT_ID', 'GRAVITEE_CLIENT_SECRET']
    .filter((k) => !process.env[k]);
  if (missing.length) {
    throw new Error(`[setup] GATEWAY_TYPE=GRAVITEE requires: ${missing.join(', ')}`);
  }
}

Gap B (QA realm): Both workflows inject REALM_KEY: 'cbpf-test23' unconditionally, overriding the setup default of cbpf-qa23 for QA. On the scheduled QA run this points Gravitee at the wrong realm.

REALM_KEY: ${{ github.event.inputs['realm-key']
  || (env.TEST_ENV == 'QA' && 'cbpf-qa23' || 'cbpf-test23') }}

Alternatively, only inject REALM_KEY when the caller supplies it, and let setup.js derive the environment-correct default.

Acceptance: Gravitee run without secrets fails immediately with a clear message; scheduled QA Gravitee run resolves cbpf-qa23.

P4
Phase 4 — Token lifetime resilience MEDIUM

Gap: Long suites (notably Migration) fetch the bearer token once in beforeAll; Gravitee token TTL may differ from Azure, causing cascading 401s mid-run (already observed on Azure).

Fix: Add a lightweight cached-token helper in api.util.ts that re-fetches when the token is near expiry (decode exp or track issue time), and have suites call getAuthHeaders() per test rather than caching a single header set.

private tokenCache?: { token: string; expiresAt: number };

public async getValidToken(): Promise<string> {
  const skewMs = 60_000; // refresh 60s before expiry
  if (this.tokenCache && Date.now() < this.tokenCache.expiresAt - skewMs) {
    return this.tokenCache.token;
  }
  const token = await this.getBearerToken();
  const ttlMs = 15 * 60_000; // conservative default; override from expires_in if returned
  this.tokenCache = { token, expiresAt: Date.now() + ttlMs };
  return token;
}

Acceptance: Full Migration batch completes without token-expiry 401s on both gateways.

P5
Phase 5 — Scope, docs & regression guardrails LOW
  • UI scope: Gravitee overrides LUMINATE_PORTAL_URL, which also affects UI suites. Confirm portal login works under Gravitee, or restrict Gravitee to backend suites and document it.
  • Regression matrix: Add a CI job that runs a Gravitee smoke batch (Calendar + one spec per family) on a schedule so Azure/Gravitee parity is continuously verified.
  • README: Document GATEWAY_TYPE/REALM_KEY/GRAVITEE_* variables and local run commands in playwright-e2e/README.md.
  • Reporting: Gateway + RealmKey already surfaced in Allure environment metadata.

8. Risk & Security Considerations

AreaRiskMitigation
Secrets handling Gravitee client secret must never be committed. Local playwright-e2e/.env holds real values. .env is git-ignored (verified). CI reads GRAVITEE_CLIENT_ID/SECRET from GitHub secrets. Rotate any secret that was ever shared in chat/docs. Bearer-token redaction (REDACT_BEARER_TOKEN) is on by default.
Route drift Gravitee gateway may not expose a specific relative path served by Azure. All relative paths are identical across gateways (only the base URL changes); a Gravitee smoke job per family catches any gateway-side routing regression.
Silent misconfiguration Wrong gateway/realm produces confusing 401/404 rather than a clear failure. Phase 3 fail-fast validation and setup logging of the active gateway/realm.
Token expiry Cascading 401s on long suites if Gravitee TTL is shorter than Azure. Phase 4 cached-token refresh helper.
Backwards compatibility Existing Azure runs must be unaffected. GATEWAY_TYPE defaults to AZURE; all Gravitee logic is behind the flag. Azure baseline is the regression gate.
