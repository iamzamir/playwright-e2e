# Plan SOP — Test Automation Strategy

> Owner: PS Automation Team · Status: Living document · Last updated: 2026-06-23
>
> This document defines **how** we test Plan SOP with automation: scope, layers, design
> principles, environments, execution, quality gates, and the metrics we hold ourselves
> to. Architecture context lives in the [Architecture diagram](../architecture/Plan-SOP-Playwright-Architecture.pdf); this document
> explains the overall *strategy* those decisions serve.

---

## 1. Purpose & objectives

Plan SOP is a backend-heavy, micro-frontend (MFE) planning application. Our automation
exists to:

1. **Protect critical business workflows** (Process Orchestration, Planning Space,
   Pages & Blocks, Scope, Scenario, Cards) from regression.
2. **Give fast, trustworthy signal** on every environment promotion (INTEROP → QA → PSR).
3. **Make failures cheap to diagnose** through redacted network capture, structured
   logs, and rich reports.
4. **Validate non-functional posture** — performance (UI metrics + JMeter API load) and
   security hygiene (no secret leakage in artifacts).

### Success criteria

| Objective | Target |
|---|---|
| Critical-path regression coverage | 100% of P0 user journeys automated |
| Nightly suite pass rate (excluding known issues) | ≥ 98% |
| Flaky-test rate | < 2% of executions |
| Mean time to diagnose a failure | < 15 min using artifacts alone |
| Secret leakage in logs/artifacts | 0 (enforced by redaction) |

---

## 2. Scope

### In scope
- End-to-end UI journeys across the MFE for the domains above.
- Process Orchestration **backend** batches (data/state-oriented flows).
- UI performance measurement and JMeter-based API performance/load.
- Cross-environment execution (INTEROP / QA / PSR).

### Out of scope (handled elsewhere)
- Unit and component tests (owned by application teams).
- Manual exploratory and accessibility audits (complementary, not replaced).
- Infrastructure/chaos testing.

---

## 3. Test layering — where each check belongs

We follow a **Testing Trophy** bias rather than a tall UI pyramid, because the app's
risk concentrates in integration and workflow behaviour.

```
        ▲  E2E UI journeys (this framework) — high value, slower, fewer
       ╱ ╲ API / backend batches (Playwright + JMeter) — broad, fast
      ╱   ╲ Component / unit (owned by app teams) — fastest, most numerous
     ╱_____╲
```

**Placement rules**
- A behaviour is automated at the **lowest layer that can prove it**.
- UI E2E covers *journeys and integration across the MFE*, not field-level validation
  that a component test could cover.
- API/backend batches verify data and state transitions without paying UI cost.
- Performance is its own track (see §8).

---

## 4. Design principles

These principles are binding for all new and migrated tests. Each maps to an ADR.

1. **Page Object Model with a BasePage facade.** Locators and journeys live in page
   objects; mechanics live in `BasePage`. (ADR-0001)
2. **Fixtures are the only way to get collaborators.** No `new <Page>()` or
   `browser.newContext` in specs. (ADR-0002, ADR-0009)
3. **Timeouts are centralized and intent-named.** No magic numbers. (ADR-0003)
4. **Suites are data, not code.** Selection via `tests/TestSuites/*.json`. (ADR-0004)
5. **Authenticate once, reuse `storageState`.** (ADR-0005)
6. **Observe and redact.** Network capture + secret redaction at every sink. (ADR-0006)
7. **Prefer native locators** (`getByTestId`/`getByRole`) over XPath. (ADR-0010)
8. **No hard waits.** Web-first assertions and real signals only. (ADR-0011)
9. **Tests are independent and deterministic.** A test sets up the state it needs and
   does not depend on another test's side effects.
10. **Assert through `expect`.** Logging helpers (`compareTwoValues`) aid readability but
    must not be the sole arbiter of pass/fail.

## 5. Test data strategy

- **Partitioned by environment:** `testdata/INTEROP`, `testdata/QA`, `testdata/PSR`.
- **Per-spec JSON data files** keyed to the spec name, loaded by environment, keep test
  inputs out of code.
- **Auth state** is a disposable cache under `testdata/.auth/` (git-ignored, never an
  artifact). Regenerated by global setup when sessions expire.
- **Principles:** data is *owned* by the test that needs it; destructive flows create
  and clean up their own data; no test depends on shared mutable seed data it does not
  control.

## 6. Environments & configuration

| Environment | Purpose | Notes |
|---|---|---|
| INTEROP | Primary integration target | Default for most suites |
| QA | Pre-release verification | Distinct realms/users |
| PSR | Performance / staging-like | Performance tracks run here |

- Environment is supplied at invocation (`ENVIRONMENT=…` via `cross-env`); the fixture
  layer reconciles the legacy `PSENV` alias into one canonical value. (ADR-0007)
- Config profiles: `playwright.config.ts` (local/CI), `playwright.sauce.config.ts`
  (Sauce grid), `performance.config.ts` (perf track).
- Tuning knobs (env vars): `PW_TIMEOUT_MULTIPLIER`, `PW_PAGE_CACHE_SCOPE`,
  `PW_NETWORK_ARTIFACT_MODE`, `PW_OBSERVABILITY_MODE`, `HEADLESS`, `SUITENAME`,
  `USE_SPECIFIC_TESTS`.

## 7. Execution model

### Local
```bash
npm run test:interop                 # full INTEROP run
npm run test:interop:poui:powerbar   # focused domain batch
npm run test:target -- tests/.../Test_001.spec.ts   # single spec (healer/autopilot)
```

### CI/CD (GitHub Actions)
- Suites are selected by setting `SUITENAME` + `ENVIRONMENT`; workflows stay thin.
- **Parallelism:** `workers: 5` in CI, `1` locally; `retries: 1` in CI, `0` locally.
- **Cloud:** `saucectl` runs the same specs on the Sauce Labs grid for scale/browser
  coverage.
- **Cadence:** nightly cron suites for UI, API, and performance; on-demand targeted runs
  for PRs/hotfixes.

### Parallelization & isolation
- Workers are isolated; the worker page cache accelerates serial flows within a worker
  without leaking state across workers. (ADR-0002)
- As specs migrate to fixtures (ADR-0009), `fullyParallel` can be revisited per domain
  once tests are provably independent (§4.9).

## 8. Performance testing

| Track | Tooling | What it answers |
|---|---|---|
| UI performance | Playwright + `performance.metrics.util` | Page/interaction timings against thresholds |
| API load | JMeter (`jmeter/Tests/*.jmx`) | Throughput/latency under concurrent load |

- Performance runs use dedicated configs and typically target PSR.
- Each performance check must define **explicit thresholds** (e.g. p95 navigation
  budget); a run fails if a threshold regresses beyond tolerance.

---

## 9. Observability & failure triage

Every run produces, on failure:
- **Redacted network capture** (request/response, sensitive headers stripped) — ADR-0006.
- **Screenshots** (`only-on-failure`) and **video** (`retain-on-failure`).
- **Structured winston logs** (with a separate error log) and an **Allure** report with
  per-step ✅/❌ markers and environment metadata.
- **Playwright traces on retry** once ADR-0012 is adopted — the primary reproduction
  artifact.

**Triage flow:** Allure report → failed step → trace/video → redacted network entry →
root cause. Target: < 15 minutes without re-running.

## 10. Quality gates

A change to the framework or specs must pass:

1. **Type check** — `tsc` clean (no new `any` in changed code where avoidable).
2. **Lint** — including the spec-hygiene rules (no direct page-object import / no
   `browser.newContext` / no `waitForTimeout` outside allowlist) as they land
   (ADR-0009, ADR-0011).
3. **Smoke suite green** — `PSSmokeBatch` passes on INTEROP.
4. **Suite-manifest validation** — every `TestSuites/*.json` references existing specs.
5. **No secret leakage** — redaction patterns cover any newly introduced token formats.

A spec is "done" only when it is independent, fixture-driven, uses web-first assertions,
and carries the right tags/data.

---

## 11. Flakiness policy

- A test that fails intermittently is **quarantined** (tagged, excluded from the gating
  suite) within one business day and tracked to closure — it is never left to silently
  re-run.
- Root cause is classified: app defect, test race (usually a hard wait — ADR-0011),
  locator drift (XPath brittleness — ADR-0010), data, or environment.
- Quarantine is temporary; a quarantined test must have an owner and a due date.
- Flaky-rate is reported every sprint (§13) and treated as a first-class quality metric.

---

## 12. Risk-based prioritization

Coverage is allocated by **business impact × change frequency × failure likelihood**.

| Priority | Examples | Expectation |
|---|---|---|
| P0 | Core Process Orchestration journeys, login/auth, Planning navigation | Fully automated; in smoke + nightly; zero tolerance for gaps |
| P1 | PowerBar, Scope, Scenario, Cards primary flows | Automated; in nightly regression |
| P2 | Secondary/edge flows, rarely changed areas | Automated opportunistically; lower cadence |

---

## 13. Metrics & reporting

Tracked per sprint and surfaced to stakeholders:

- Pass rate (gating suite) and trend.
- Flaky-test rate and open quarantine count.
- Mean suite duration and p95 spec duration (watch for hard-wait regressions).
- Coverage of P0/P1 journeys.
- Failure MTTR (time from red build to identified cause).
- CI cost signals (Sauce minutes, run time) to keep the suite economical.

## 15. Roadmap (from the Proposed ADRs)

The near-term engineering investments that move us from "good framework" to "well-governed
platform":

1. **ADR-0009** — migrate all specs to consume fixtures; add the lint/CI guard.
2. **ADR-0011** — eliminate hard waits in favour of web-first assertions.
3. **ADR-0010** — migrate XPath to `getByTestId`/`getByRole`.
4. **ADR-0012** — enable `trace: 'on-first-retry'` and upload traces in CI.
5. Converge the `ENVIRONMENT` / `PSENV` duality onto a single canonical variable
   (follow-up to ADR-0007).
