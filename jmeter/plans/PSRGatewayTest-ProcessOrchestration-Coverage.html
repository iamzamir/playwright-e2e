Overview

After phase 1, the plan's 116 PO samplers cover 31 of the 58 PO routes the two UIs call, up from 18 routes in 83 samplers. Phase 1 added process context and scope, all Calendar Manager routes, and supply chain action CRUD. What's still missing is the entity-limit and scenario-validation reads, Settings transitions and templates, action item bulk and by-ID reads, and the process lifecycle writes. In this report, process and subprocess routes count as separate endpoints.

Planning Space process context is now covered

planning-mfe calls GET /process/{p}/context?all=true every time Planning Space opens (SideNavWithRightPanel.didGetProcessContext). Phase 1 added it to the "PO To PS", "Subprocess To PS" and "Action Items To PS" controllers. It also added sequential POContext1 and POContext2 samplers, which extract the calendar and cycle names for the calendar reads.

Scenario quota validation calls other services

POST /process/{p}/validate/SCENARIO?isAsync=false runs when the Scenario table loads. It finds every process that shares the template, then calls the foundation simulation service and the assumptions service before it returns. If a request leaves out isAsync=false, the default is async, and the service writes a job row on every call.

PO process pages skip the entity-limit lookup

lui calls GET /process/{p}/entity/ACTION_ITEM when a user enters a process (SideNavTabPanel) and when a process is opened from the listing. The call merges template, tenant and default quota limits. It's missing from "PO Details Page", "Subprocess Details Page" and the "PS To" controllers.

Older samplers are still not asserted

All 33 phase 1 samplers assert the response code and the body. The 83 older PO samplers still have no assertions, so a 4xx or 5xx response from them still counts as a normal sample. Also, "Subprocess Details Page 7" and "PS To Subprocess 7" read KPIs for IntegratedBusinessPlanning/subprocess/subprocess1, while the other samplers in those controllers use PSR1/subprocess1. Check that this pair exists in PSR.

Common request details

Every call below uses the same base URL, token and headers as the PO samplers already in the JMX.

Base URLhttps://${API_HOST}/cbp/psr/ibp/process-orchestration/v1 → https://api-psrtest.jdadelivers.com/cbp/psr/ibp/process-orchestration/v1. planning-mfe (pltpsr.apiURL) and lui (psr: cbp/psr/ibp + /process-orchestration/v1, config.apis.poAPIUrl) use the same base. In both UIs, useApi adds this base to any URL that doesn't contain http.
HeadersContent-Type: application/json
Authorization: Bearer ${__property(access_token)}
accept: application/json
RBACProcess, subprocess and calendar routes carry @PreAuthorize("@ibp.hasAction('RBAC_PROCESS.<name>', {'LSNOP_VIEW'})") or the matching CREATE, EDIT, DELETE, START or STOP action. The client-credentials identity needs those rights on each process. The existing GET /process/{p} samplers already depend on the VIEW right.
ErrorsLocalExceptionHandler extends the rbac-lib GlobalExceptionHandler and returns an ApiError body. Any exception it doesn't map becomes UNHANDLED_EXCEPTION. PO error codes use the form IBP_PO_50_<code>: 2002 PROCESS_NOT_FOUND (404), 2042 LAST_CYCLE_REACHED (500) and 2043 ERROR_MOVING_CYCLE (500). lui reads the code from errors[0].errorCode.
ShapesMany PO routes return Map<String,Object> built by stored procedures, and have no DTO. For those routes, the samples below show only the keys the service code or the UI reads. All values are illustrative, not captured from PSR.

P1POST /process/{p}/validate/SCENARIO?isAsync=false ProcessController · no RBAC annotation
URL
https://api-psrtest.jdadelivers.com/cbp/psr/ibp/process-orchestration/v1/process/IntegratedBusinessPlanning/validate/SCENARIO?isAsync=false
Called by
planning-mfe: ScenarioQuotaLimitWarning mounts on the Scenario table and dispatches getScenarioQuotaLimitDetails() in reducers/scenario_quota_limit.ts. The URL comes from config.getScenarioQuotaLimit, and the request has no body. The UI stores $.status, which drives the soft or hard limit banner.
Service work
EntityServiceHelper.validate() looks up the template ID, the quota limits for the tenant and global scope, and the default thresholds. Then it lists every process that shares the template. ScenarioEntity.validate() calls simulationProxyService.getScenarios(processNames, "PROCESS") and assumptionProxyService.getAssumptionIds(processIds). If there are assumptions, it calls getScenarios(…, "ASSUMPTION") as well. That's two or three downstream HTTP calls per request. If the template or entity isn't found, the service returns SUCCESS straight away. If the call has no isAsync parameter, the default is true: the service inserts a job_execution_status row and returns a statusUrl.

Request

No body. An optional EntityLimitDto is { "operations": ["…"] }; without it, the service checks every configured operation.

Response · 200 (sync)

{ "status": "SUCCESS", "message": "Validated Successfully" }

Other values are "WARNING", with the limit message, and "ERROR", with the exception message. Both still return HTTP 200.

Response · 200 (async, if isAsync is left out)

{ "statusUrl": "/job/{jobId}/status" }

Add to the JMX: add a standalone "Scenario Table" sampler that always sends ?isAsync=false. Assert 200, and assert that $.status isn't ERROR. Watch its latency: most of it comes from the foundation simulation service.

Behaviour

  • The transition runs asynchronously; poll statusUrl.
  • Starting a process that's already IN_PROGRESS returns the previous job ID.
  • Starting a COMPLETED process moves it to the next cycle. If the calendar has no cycles left, the call fails with IBP_PO_50_2042 (LAST_CYCLE_REACHED); a failed move gives 2043. lui shows its "cannot start" modal for both.
  • Stopping doesn't undo a cycle move. Leave this out of steady-state load.

POST /process/template → POST …/subprocess → PUT …/subprocess/{s} → DELETE …/subprocess/{s} → DELETE /process/{p}, with names unique per thread. Leave start/stop, planstartdate and reschedule out of steady-state load: they change the process's cycle and schedule, and can't be undone in the same iteration.

Data rules, from the PO service code
  • PUT /process/{p}/scope stores the whole body as the new scope, and every later context call returns it. A partial body on IntegratedBusinessPlanning changes Planning Space for everyone.
  • validate/{entityName} is async unless isAsync=false is sent; every async call inserts a job row.
  • Starting a completed process moves it to the next cycle. Once the calendar runs out, starts fail with IBP_PO_50_2042.
  • Bulk action item creation makes one item per template entry in the actionitems service. Delete them in the same iteration.
  • All threads share one client-credentials identity. Give per-thread names to anything a thread creates (calendars, processes).

How this report was built
  • UI usage comes from a static scan of non-test files in plan-sop-planning-mfe/src and plan-sop-lui/src. The scan covered every URL passed through useApi (any URL without http gets the PO base) and every config.apiURL, config.tenantDetails and config.apis.poAPIUrl route, each traced to its caller. No browser trace or gateway log was used.
  • JMX coverage comes from the HTTPSampler.path and HTTPSampler.method of every sampler in jmeter/Tests/PSRGatewayTest.jmx whose path contains process-orchestration/v1.
  • Request and response shapes come from the PO controllers, DTOs and service code: ProcessService, NodeService, EntityServiceHelper, ScenarioEntity, MeteringService, ActionItemProxyService and TransitionService. PSR samples come from playwright-e2e/testdata/PSR/ProcessOrchestrationBackend. Values are illustrative.

  • Phase 1 was smoke-tested on 24 Sep 2026 with 1 thread for 60 s: Azure run 35965364407 and Gravitee run 35965406527. The only failure was the over-strict POScope1 assertion, which is now fixed.
