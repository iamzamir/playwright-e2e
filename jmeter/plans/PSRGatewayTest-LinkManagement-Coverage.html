Overview

After PR #726 the plan drives all 19 LM endpoints that the two UIs call. The PR adds 18 samplers. They cover the bulk view lookup that runs on every Planning Space load, the single-mapping, scope and favourites writes, and the preset and maasactor search payloads the plan didn't send.

19not called by either UI

The heaviest LM read is now in the plan

LMSearch1 sends POST /view-entity-map/lm-search/v2 as one standalone sampler. It checks that $.views exists, not that it's non-empty, so a failed group query (which still returns 200) isn't caught.

Scope is written as well as read

ScopeMapping1 saves a scope for a per-thread view and ScopeMapping2 resets it to null. LM has no DELETE for scope, so one scope row per thread remains.

Mapping writes run one call at a time

ViewEntityMap1–4 map and unmap a maasactor and a procedure, and ViewEntityMapSearch1 reads the mapping back. The Duplicate view chain and its parallel PUT burst aren't modelled.

Favourites and preset variants are exercised

Favourites1–4 add and remove on both routes, with JSON extractors carrying the id. PresetVariant1–6 send the global, subprocess-context and admin "apply to all users" payloads.

Common request details

Every call below uses the same base URL and headers as the LM samplers already in the JMX.

Base URL https://${API_HOST}/cbp/psr/ibp/links/v1 → https://api-psrtest.jdadelivers.com/cbp/psr/ibp/links/v1. It's the same base that planning-mfe (pltpsr.apiLinksURL) and lui (psr: cbp/psr/ibp + /links/v1) use.
Headers Content-Type: application/json
Authorization: Bearer ${__property(access_token)}
accept: application/json
Token Comes from "Thread Group - Bearer Token" (B2C client-credentials policy B2C_1A_ClientCredential). Every load thread shares this one identity, so per-user data (favourites, presets) all belongs to a single LM user.
Errors Bean-validation failures and missing required query parameters return 400; an invalid token returns 401. Both are asserted in Test_010_ScopeMapping.spec.ts. Error bodies are ApiError objects from plan-sop-rbac-lib.
Null fields LM sets no global Jackson inclusion rule, so DTOs without @JsonInclude(NON_NULL) return their null fields. Every ViewDto in the samples below does this.

URL
https://api-psrtest.jdadelivers.com/cbp/psr/ibp/links/v1/view-entity-map/lm-search/v2
Called by
planning-mfe, every time Planning Space opens: SCASideNav mounts on the process-plan page and calls getEntities() → getViewsWithMappedEntities() (src/hooks/useFetchAllActors.ts). It's also called from refreshEntities() and from Action Planner → Scenario Scope (MaasActorScope.tsx).
Payload source
Actor names from foundation actorsConfig, grouped into uicacheactor, scsactor, insightactor and maasactor. Procedure names from foundation proceduresConfig, as SCP-Launch-Interactive-Planning. Groups with no names are dropped.
Why it matters
It's the highest-volume LM read. The service runs one DB query per group on the JVM common ForkJoinPool (CompletableFuture.supplyAsync with no executor), so one call means up to 5 parallel queries against a pool capped at 100 connections. If any group's query fails, the error is only logged and the call still returns 200 with {"views": []}. A failure looks exactly like "no views".
Validation
requests must not be empty, and each item needs a non-empty entityId list and an entityType; otherwise 400.

Where PR #726 differs from the original recommendations
  • lm-search/v2 is one standalone sampler, not in the "PO To PS", "Subprocess To PS" and "Action Items To PS" parallel controllers. It sends 8 names, not the 76 procedure names, and doesn't assert that $.views is non-empty.
  • The Duplicate / Save as chain below isn't modelled as a chain. The mapping PUTs run one after another, not as a parallel burst, and the new view isn't mapped with POST /view-entity-map or POST /entity-view-procedure-map.
  • Favourites use a dummy viewId + containerId pair fixed per thread, not a real pair, so one catalogue view per thread remains. The "PO To PS 10: Views" read isn't between add and remove.
  • Not driven: the assumptiontype search, the uicacheactor, scsactor and insightactor per-type searches, and the admin preset for a subprocess.

Original recommendations (for reference)

P1 A. Planning Space load

Add POST /view-entity-map/lm-search/v2 to the "PO To PS", "Subprocess To PS" and "Action Items To PS" parallel controllers, and assert that $.views isn't empty. Keep "PO To PS 7" only if you also want lui's per-type search pattern.

P1 B. Duplicate / Save as view (planning-mfe SettingsDialog)

Use a new Transaction Controller, with the calls in UI order:

  1. POST /view-entity-map: the full ordered view list for ${processName}, including the new view.
  2. PUT /view-entity-map/views/${newViewId}/type/{actorType}/entity/{actor}: one per actor type, inside a Parallel Controller.
  3. PUT /view-entity-map/views/${newViewId}/type/SCP-Launch-Interactive-Planning/entity/{procedure}: the default procedure.
  4. PUT /scope?entityType=subprocess&entityId=${processName}&viewId=${newViewId}: the source view's scope.
  5. POST /entity-view-procedure-map with "views": ["${newViewId}"].

Clean up with DELETE for each actor and procedure mapping, and PUT /scope with { "scope": null, "quickFilterEnabled": false }.

  1. PUT /view-entity-map/views/{view}/type/maasactor/entity/{actor}
  2. POST /view-entity-map/search with "entityType": "maasactor"
  3. DELETE /view-entity-map/views/{view}/type/maasactor/entity/{actor}
  4. POST /view-entity-map/search again, to confirm the mapping is gone

  1. POST /entity/${linkEntityId}/views, with a JSON Extractor from $.id into favouriteId
  2. The existing "PO To PS 10: Views" read
  3. DELETE /entity/${linkEntityId}/views/${favouriteId}
  4. Repeat on the typed subprocess routes (add, remove)

  1. POST /preset with "applyToAllUsers": true and entityName
  2. POST /search-preset
  3. POST /preset/clear with "applyToAllUsers": true
Data rules, from the LM service code
  • POST /view-entity-map deletes every existing mapping of the entities in the request, then inserts the views you sent. Always send the full ordered view list. Only send it for CSV perf entities (LinksData.csv), never a partial list for IntegratedBusinessPlanning.
  • LM has no DELETE for scope. Random per-iteration view IDs leave one scope row per iteration, so use a fixed view ID per thread.
  • Adding a favourite creates a catalogue view when the viewId and containerId pair is new, and removing it never deletes that view. PR #726 uses one dummy pair per thread, so this is bounded to one catalogue view per thread.
  • All threads share one client-credentials token, so favourites and presets all belong to one LM user. PR #726 gives each thread its own view ID to avoid same-row contention.
  • The admin preset flow ("applyToAllUsers": true) needs a process that LIAM knows on the tenant; otherwise it fails with LIAM_RESOURCE_NOT_FOUND. It writes one preset per LIAM user of that process. PR #726 writes them for the dummy per-thread view and clears them in the same iteration.
  • Every LM sampler added in PR #726 has response assertions. The older LM samplers still have none.
